# Nexus frontend concept

A buildless frontend sketch of a connected B2B business workspace.

Run the complete app with `npm ci` then `npm run dev`, and visit http://localhost:4173. Open `/builder` for the integrated Puck website builder. `npm test` runs validation/persistence tests; `npm run build` and `npm start` run the production build locally.

Includes Overview, Websites, Templates, Website Builder, CRM (contacts, leads, customers, pipeline), Campaigns, AI Agent, Workflows, Analytics, Webinars, Billing (subscriptions, plans, usage), and Settings.

## Google Calendar connection for webinars

The webinar dashboard supports multiple events, public registration pages, CRM-linked registrations, attendance CSV import, and consent-based follow-up message drafts. For this local setup, set `PORT=4190` and register the exact callback URL `http://localhost:4190/api/webinars/google/callback` in Google Cloud (use the matching host and port if you change it). Enable Calendar API, configure Google Auth Platform, add the organizer as a test user while the OAuth app is in Testing, and grant `https://www.googleapis.com/auth/calendar.events`. Set `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET`, `GOOGLE_REDIRECT_URI`, and a stable `WEBINAR_TOKEN_ENCRYPTION_KEY` (generate one with `node -e "console.log(require('node:crypto').randomBytes(32).toString('hex'))"`) in the ignored local `.env`. The refresh token is encrypted in ignored `.nexus-data/`. Restart the server and connect the organizer account from the Webinars page. Publishing a draft while Calendar is connected creates a Calendar event with a Meet link. Attendees receive a Calendar invite and a direct Meet link after registering. Attendance is entered by importing a CSV with `email,minutesAttended` columns; the app categorizes attendance as no-show (0 min), partial, or attended (75%+ of event duration). Follow-ups create subject/body message drafts for consented attendee or no-show audiences; they are not sent because outbound email is not configured. Deleting an event removes its registrations and follow-up drafts and attempts to remove its Calendar event, which can send cancellation notices. The prototype has no workspace login, so keep it local/private until access control is added.

The default homepage tells the Nexus story through an interactive customer journey, four example project showcases, product mockups, an AI planning storyboard, and FAQs. Open `/#projects` for the project workspace, or `/#overview` for the business dashboard. Project filters, search, grid/list views, details, and journey tabs are temporary UI interactions.

The Website Builder uses Puck 0.23, controlled React sections, three structured templates, shared theme tokens, durable local project storage, reviewed AI change proposals, clean preview routes and published snapshots. The default composer is a clearly labeled deterministic demo; a server-side OpenAI-compatible provider can be configured without changing the editor. See [implementation notes](docs/WEBSITE_BUILDER.md) for the architecture diagram, file map, environment, workflows and limitations.

The commercial visual system and design sources are documented in `DESIGN.md`. Showcase brands and customer projects are fictional concepts, not endorsements or verified customer results.

The existing business dashboard data remains illustrative. The builder now has a server API and project persistence in ignored `.nexus-data/`, but no authentication, payments, email, scraping or live CRM connections. Actual AI calls require a configured server provider; default demo generation needs no keys. Published routes are local to the running server. Legacy homepage fonts use Google Fonts with system fallbacks; website templates use system fonts.

## Local working billing console

Node.js 24 or later is required. Run `npm run billing:dev` from this directory and open `http://127.0.0.1:4175/console.html` for the working console. The original concept remains at `/` on the same port. The local server stores demo records in `data/nexus.sqlite`, which is ignored by Git. Run `npm run billing:test` for the single-account checkout, plan-change, cancellation, and webhook checks.

Sign in with the single demo account, `nexus@nexus.demo`. Its local password defaults to `NexusDemo!2026`; when `NEXUS_DEMO_PASSWORD` is set in `server/.env`, the account uses that password after the server starts. The sign-in form does not fill in the password. Older demo identities remain in the local database solely to preserve historical test records and cannot sign in. The server binds only to `127.0.0.1` and uses HTTP-only, same-site session cookies. This is not a production identity system.

The one demo account can create monthly INR plans, link a Razorpay **test** plan, record usage, view the audit trail, and buy a subscription directly through Razorpay Test Mode checkout. It can submit plan changes and immediate cancellations directly to Razorpay for provider-backed subscriptions. The seeded `customer@nexus.demo` subscription is an illustrative historical record with no Razorpay subscription ID and cannot be changed at the provider. Gemini drafts plans but has no billing tool access. Verified webhooks determine final subscription and payment status.

For Razorpay test-mode testing, configure `RAZORPAY_TEST_KEY_ID`, `RAZORPAY_TEST_KEY_SECRET`, and `RAZORPAY_WEBHOOK_SECRET` in `server/.env`. The three monthly INR plans have been created and linked in Razorpay Test Mode. The demo account can create any newly added test plans from the console, or link an existing `plan_...` ID; Nexus checks interval, currency, and amount when linking. Direct checkout charges the first month upfront as a subscription add-on, then starts 11 recurring monthly cycles 30 days later and returns Razorpay's `short_url`. Retrying a new checkout in `created` status reuses its link. An unauthorised old ₹5 checkout is canceled and replaced; an authorised old subscription must be canceled before buying again. Upgrades are submitted immediately, downgrades at the cycle end, and cancellations immediately. Configure a **Test Mode** webhook to `https://YOUR_PUBLIC_TEST_HOST/api/razorpay/webhook` for subscription lifecycle and charge events. Razorpay webhook delivery requires a public HTTPS URL; localhost is only suitable for local requests or a separately configured tunnel. The webhook uses the raw-body `X-Razorpay-Signature` and `x-razorpay-event-id` for verification and deduplication. Set `GEMINI_API_KEY` to enable the drafting endpoint; `GEMINI_MODEL` defaults to `gemini-3.8-flash`. Live Razorpay keys are not accepted by this local service.

This is a local integration foundation, not a deployed production service. Razorpay Test Mode connectivity and creation of the three plans were verified locally; checkout completion, subscription changes, payments, and live provider webhooks remain unverified. Plan limits are stored but are not enforced in the other modules. Automatic suspension after the five-day payment grace period, tax invoice handling, refund execution, production identity, deployment, and broader connected workflow execution are still outstanding.
